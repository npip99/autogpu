# A1 — PDN macro-grid fix (PSM-0069 floating macro power pins)

> **Status: RESOLVED.** Fixed by adding a `define_pdn_grid -macro`
> + `add_pdn_connect -grid macro_grid -layers {M5 M6}` and `{M6 M7}` to
> `tech/asap7/orfs/compute_array.pdn.tcl`. Post-fix:
> `verify_macro_power.tcl` reports `ok=264 fail=0` on
> `compute_array_tiny_bcast0` and `ok=12752 fail=0` on the full 32×32
> `compute_array` post-PDN ODB. Kept here as historical context for
> future contributors investigating PSM-0069-class bugs.

## Problem

After running `compute_array_tiny_bcast0` through ORFS with the existing
`tech/asap7/orfs/compute_array.pdn.tcl`, the post-route ODB shows zero
parent power-net shapes overlapping any of the 264 hardened-macro
VDD/VSS pins. Silicon would have ~264 floating power instances per
tiny — guaranteed brown-out.

Verification reproducer:
```
openroad -exit \
  -db build/orfs/results/asap7/compute_array_tiny_bcast0/base/6_final.odb \
  tech/asap7/orfs/scripts/verify_macro_power.tcl
# Currently prints: verify_macro_power: ok=0 fail=264
```

Root cause (observed, not hypothesized):
- Leaf abstract LEFs expose macro VDD/VSS power pins on M6 at the leaf's
  internal followpin pitch (rows at y∈{129.2, 134.6, 140.0, 145.4, …},
  5.4 µm spacing).
- Parent `pdngen` from `compute_array.pdn.tcl` defines a single grid
  named `top` with M5/M6/M7 stripes at pitch 27.5 µm, offset 8.54 µm
  (channel-aligned).
- Parent stripes never overlap macro pins (different y values, different
  x ranges). pdngen also emits orphan stub segments at macro-pin y but
  in non-overlapping x — those are the PSM-0038 warnings in
  `6_report.log`.
- The pdngen grid in `compute_array.pdn.tcl` has no `-macro` grid; only
  parent-stripe-to-parent-stripe `add_pdn_connect` rules. There is no
  rule telling pdngen "weld parent stripes to leaf macro pins."

Same problem recurs at chip_top (whenever compute_array, smem, etc. are
placed as hardened macros under chip_top).

## Acceptance criteria

1. `tech/asap7/orfs/scripts/verify_macro_power.tcl` exits 0 on
   `compute_array_tiny_bcast0` post-route ODB. No `FAIL:` lines.
2. `6_report.log` for the same run reports zero PSM-0069, PSM-0039, and
   PSM-0038 messages (or only a documented small residue of stubs that
   pdngen flags but verify_macro_power confirms is irrelevant).
3. The same fix applied to the full 32×32 `compute_array.config.mk`
   produces a verify-clean route.
4. The same PDN strategy carries to chip_top — parent stripes at
   chip_top must be able to weld to compute_array's outermost power pins
   (which will be on M7 or M8 in the compute_array abstract LEF).

## Constraints

- **Must NOT regress channel-aligned stripe pattern.** The reason
  `compute_array.pdn.tcl` exists is that ORFS's stock
  `BLOCKS_grid_strategy.tcl` is O(stripes × macros) and chokes >20 min
  on 1089 macros. Any solution must not reintroduce that path.
- **Must NOT change leaf modules.** Leaves are hardened. Their LEFs/LIBs
  exist under `build/orfs/results/asap7/<leaf>/base/`. Re-hardening 12
  leaves is hours of compute and would invalidate other in-flight work.
  If the fix conceptually requires leaf-side changes (e.g., adding a
  top-layer power pin), document the requirement but do NOT execute
  re-hardening in this task — leave that as a follow-up.
- **Must NOT touch macro placement.** The 1089-instance
  `macro_placement.tcl` is generated by
  `scripts/gen_compute_array_floorplan.py`; macro positions are fixed.
- **Must work for both the tiny 4×4 (`compute_array_tiny_bcast0`) and
  the full 32×32 (`compute_array.config.mk`)** with the same PDN tcl.
- **Iterate on the tiny first.** Full 32×32 takes hours per run. Tiny
  is ~5 minutes end-to-end. Validate fix on tiny, then run full.
- **Don't touch `HOLD_SLACK_MARGIN`** — that's A2's domain.
